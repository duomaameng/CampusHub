## 2. AI 助力分析（Q1）

本阶段 AI 最大的贡献是：快速给出架构候选方案、对比维度和 ADR 文档骨架，帮助团队把“为什么不选微服务/事件驱动/中间件”说清楚。

不同 Prompt 策略下 AI 回答质量的差异：

- **直接问**时，AI 倾向于给出“成熟平台通用套餐”，包含 Redis、消息队列、微服务等不必要建议。
- **提供项目约束**后，AI 能明显收敛到分层单体，并主动说明为什么不选微服务。
- **要求多方案对比**时，AI 输出最适合转成候选方案表。
- **要求扮演架构师评审**时，AI 更容易关注订单一致性、权限、隐私和演进路径等质量属性。

## 3. AI 误导分析（Q2）

- **问题1：AI 容易默认推荐中间件。**  
  **如何发现：** 直接咨询时，AI 推荐 Redis 缓存、消息队列通知、Elasticsearch 搜索。  
  **如何修正：** 人工结合 P1 约束判断当前并发和数据量不需要中间件，改为 MySQL 通知表、HTTP 轮询、MySQL 索引和 Spring Task。

- **问题2：AI 容易高估微服务收益。**  
  **如何发现：** AI 会把“可扩展性”作为优点，但没有计算服务拆分带来的部署、联调、事务和日志成本。  
  **如何修正：** 在候选方案对比中加入“团队学习成本”“10 周内可行性”“数据一致性”维度，最终排除微服务。

- **问题3：AI 初稿对订单状态一致性强调不够。**  
  **如何发现：** P1 用例里订单存在接单、确认、完成、争议、取消等多个状态，如果各模块直接改状态会出现非法流转。  
  **如何修正：** 架构文档规定订单状态统一由 OrderService 处理，使用事务、状态枚举和状态日志。

- **问题4：AI 对团队人数理解可能不一致。**  
  **如何发现：** P1 需求文档部分文字写过“4人团队”，但 P0 团队章程和 P1 约束明确是 3 人团队。  
  **如何修正：** P2 文档统一按 3 人团队编写；“架构辩论赛”按 4 个角色记录，说明王胜晟兼任需求与测试角色。

## 4. Prompt 改进计划（Q3）

上阶段（P1）提出的改进措施，验证结果：

1. **提供上下文锚点：有效。** 把 P1 总结的校园核心需求、排除功能、团队规模和技术栈写进 Prompt 后，AI 输出明显更可用。
2. **引入反例：有效。** 明确告诉 AI “不要推荐超出学生团队能力的复杂方案”，能减少微服务和中间件堆叠。
3. **迭代提示：有效。** 先让 AI 生成架构候选，再人工指出“中间件过重”“缺少一致性分析”，第二轮结果更贴近项目。

本阶段新的改进措施：

- 在架构类 Prompt 中显式列出 **不可选项**，例如“不使用 Redis、消息队列、网关、Elasticsearch”。
- 要求 AI 输出 **为什么不选某方案**，避免只写被选方案的优点。
- 要求 AI 按 **质量属性** 评审：一致性、安全性、可维护性、可测试性、部署成本。
- 对 AI 给出的技术组件增加人工分类：哪些是 MVP 必须，哪些是后续演进，哪些当前不采用。

## 5. 本阶段的核心工程判断

**决策内容：** CampusHub 首版采用前后端分离的分层单体架构，技术栈固定为 Vue3 + Spring Boot + MySQL，不引入缓存、消息队列、网关、搜索引擎等中间件。

**为什么 AI 无法做这个决策：**

AI 可以罗列架构模式和主流技术，但它不知道团队真实开发能力、课程验收重点、服务器条件和成员熟悉程度。直接让 AI 推荐时，它更容易套用商业平台模板。最终取舍必须由团队根据 P1 需求边界和 10 周交付风险判断：我们要优先完成稳定可用的业务闭环，而不是展示复杂架构。

## 6. 本阶段人工审查结论

- 已保留 AI 提供的结构化表达、对比表和 ADR 模板。
- 已删除 AI 推荐的 Redis、RabbitMQ/Kafka、API Gateway、Elasticsearch 等非必要组件。
- 已补充订单状态流转、模块依赖、REST API 示例、部署方式和后续演进计划。
- 已统一项目技术栈为 Vue3、Java Spring Boot、MySQL，符合用户指定约束。
