# P4 开发先后顺序与并行开发计划

## 1. 说明

本文件用于说明 `CampusHub` 在 P4 编码开发阶段的推荐开发顺序，以及在 3 人团队分工下，哪些模块应按前后依赖顺序推进，哪些模块适合并行开发。

本计划基于以下已确定前提：

- `P1` 已明确核心需求范围与优先级
- `P2` 已明确采用前后端分离、分层单体、MySQL 单库架构
- `P3` 已明确 API、数据库结构、类图和核心模块边界
- 团队为 3 人，且应优先保证 `P0/P1` 主流程可运行、可联调、可演示

本阶段的总原则是：

- 先搭地基，再打通主链
- 先保证可运行，再追求完整体验
- 先完成核心闭环，再补支撑模块
- 先保证主流程稳定，再推进测试与收尾

---

## 2. 总体开发顺序

推荐按以下顺序推进：

1. 工程骨架与数据库初始化
2. 用户认证与权限基础
3. 需求发布与公开浏览
4. 接单申请、确认接单与订单创建
5. 订单状态流转与订单闭环
6. 评价与信用基础版
7. 通知、文件上传、聊天、举报、公告等支撑模块
8. 单元测试、集成测试、CI/CD、Bug 修复与演示准备

这个顺序的核心原因不是“哪个简单先做”，而是“哪个是别人的前置依赖先做”。

例如：

- 没有用户认证，就无法做发布、接单、发消息、评价和举报
- 没有需求模块，就无法做接单和订单
- 没有订单模块，就无法做订单聊天、评价和通知联动

---

## 3. 分阶段开发顺序

### 3.1 第一阶段：工程骨架与数据库初始化

#### 本阶段任务

- 初始化后端 Spring Boot 工程结构
- 初始化前端 Vue3 工程结构
- 导入数据库 DDL 和基础测试数据
- 完成统一响应结构、全局异常处理、基础配置
- 完成前端路由、Pinia、Axios 请求封装

#### 为什么最先做

这是整个系统的“地基”。如果前后端工程都没有稳定启动方式，后面的模块开发会不断返工。

#### 推荐分工

- 王自宽：后端工程骨架、统一响应、全局异常、基础配置
- 蔡利扬：前端工程骨架、路由、状态管理、请求封装
- 王胜晟：数据库初始化脚本、测试数据、运行脚本

#### 可并行开发

- 后端骨架
- 前端骨架
- 数据库初始化

这三块可以同时开始，互相依赖较弱。

---

### 3.2 第二阶段：用户认证与权限基础

#### 本阶段任务

- 注册
- 登录
- 邮箱验证码
- 用户资料页
- 认证状态控制
- 前端登录态和页面权限跳转

#### 为什么排在这里

因为后面的发布需求、接单、发消息、评价、举报都依赖用户身份和权限。

#### 推荐分工

- 王自宽：注册、登录、验证码、资料接口、认证逻辑
- 蔡利扬：登录页、注册页、个人资料页、登录态与路由守卫
- 王胜晟：准备测试账号、权限测试数据、接口调试支持

#### 可并行开发

- 用户认证后端接口
- 登录注册前端页面
- 测试账号与基础接口测试

---

### 3.3 第三阶段：需求发布与公开浏览

#### 本阶段任务

- 任务大厅列表
- 任务详情
- 发布需求
- 我的发布
- 分类字段和基础校验

#### 为什么排在这里

因为没有“需求”，平台就没有后续的接单与订单流程。  
这一步完成后，系统就能初步体现“校园互助平台”的核心价值。

#### 推荐分工

- 王自宽：需求列表、详情、发布、编辑/删除接口与校验
- 蔡利扬：任务大厅页、详情页、发布页、我的发布页
- 王胜晟：配图上传基础支持、测试数据整理

#### 可并行开发

- 需求模块后端
- 任务大厅/详情/发布前端
- 文件上传基础能力

#### 阶段目标

到这一步，系统应能做到：

- 游客浏览公开需求
- 已登录用户进入系统
- 已认证用户发布需求并查看详情

---

### 3.4 第四阶段：接单申请、确认接单与订单创建

#### 本阶段任务

- 申请接单
- 查看申请列表
- 确认接单
- 生成订单
- 订单详情
- 我的接单 / 我的订单列表

#### 为什么这是主链核心

这是“需求帖子”进入“正式执行流程”的分界点。  
从这一步开始，系统从信息展示平台变成真正有业务状态的服务平台。

#### 推荐分工

- 王自宽：申请接单、确认接单、订单创建、订单查询接口
- 蔡利扬：我的发布、我的接单、订单详情页面
- 王胜晟：通知模块骨架，因为接单后很快需要通知能力

#### 可并行开发

- 申请/成单后端
- 订单详情和订单列表前端
- 通知基础模块

#### 不建议多人同时深改的部分

- `OrderService`
- 订单状态字段和状态枚举
- 核心订单表结构

这些部分由王自宽主导最稳妥，避免多人同时改造成联调混乱。

---

### 3.5 第五阶段：订单状态流转与订单闭环

#### 本阶段任务

- 订单进行中
- 提交完成
- 确认完成
- 取消订单
- 订单状态日志
- 核心状态流转单元测试

#### 为什么单独列一阶段

因为这部分不是简单 CRUD，而是整个系统最重要的业务规则中心。  
我们在 `P2/P3` 已经明确：订单状态必须由 `OrderService` 统一处理。

#### 推荐分工

- 王自宽：状态流转、事务控制、状态日志、单元测试
- 蔡利扬：订单详情页中的状态按钮、状态展示、异常提示
- 王胜晟：状态变更通知触发点、异常流程测试支持

#### 可并行开发

- 订单状态流转后端
- 状态相关前端交互
- 通知联动与异常测试

#### 阶段目标

到这一步，主链应该可以跑通：

`注册登录 -> 发布需求 -> 申请接单 -> 确认接单 -> 生成订单 -> 完成订单`

---

### 3.6 第六阶段：评价与信用基础版

#### 本阶段任务

- 双向评价
- 防止重复评价
- 评价记录展示
- 基础信用流水

#### 为什么放在订单闭环之后

因为评价依赖“订单已经完成”，它是主流程的收尾功能，而不是前置功能。

#### 推荐分工

- 王自宽：评价接口、重复评价拦截、信用流水基础逻辑
- 蔡利扬：评价弹窗、评分与评价结果展示
- 王胜晟：评价邀请通知、评价相关测试

#### 可并行开发

- 评价后端
- 评价前端
- 评价通知与测试

---

### 3.7 第七阶段：支撑模块并行补齐

这一阶段的特点是：  
它们都很重要，但不属于主链最早的前置依赖，因此更适合在主链后半段并行推进。

#### 3.7.1 通知模块

##### 本阶段任务

- 接单申请通知
- 订单状态变更通知
- 评价邀请通知
- 举报结果通知
- 已读处理

##### 推荐分工

- 王胜晟主导后端通知逻辑
- 蔡利扬完成通知中心页面与未读提示

##### 可以开始的时间

从“申请接单 / 订单创建”阶段开始就可以逐步接入。

---

#### 3.7.2 文件上传

##### 本阶段任务

- 头像上传
- 任务配图上传
- 聊天图片上传
- 举报证据上传

##### 推荐分工

- 王胜晟主导上传接口与存储路径策略
- 蔡利扬对接前端上传组件

##### 可以开始的时间

在需求发布阶段就可以开始，不必等订单模块全部完成。

---

#### 3.7.3 聊天模块

##### 本阶段任务

- 订单内文字消息
- 图片消息基础版
- 历史消息查询

##### 为什么不能太早做

因为聊天依赖：

- 订单已经存在
- 用户身份和权限已经明确
- 订单参与者关系可校验

##### 推荐分工

- 王胜晟：后端消息接口、WebSocket、消息落库
- 蔡利扬：订单详情页聊天区域

##### 可以开始的时间

订单详情稳定后最适合接入。

---

#### 3.7.4 举报与公告后台

##### 本阶段任务

- 举报提交
- 举报列表
- 管理员处理举报
- 公告发布/下线
- 前台公告查看

##### 推荐分工

- 王胜晟：举报、公告、后台基础接口
- 蔡利扬：基础管理页面和公告展示页

##### 为什么放在后面

它们属于平台治理和运营能力，重要但不属于首条主链的前置依赖。

---

### 3.8 第八阶段：测试、CI/CD、Bug 修复与演示准备

#### 本阶段任务

- 单元测试补齐
- 集成测试
- CI/CD 配置
- Bug 修复日志整理
- 演示说明和运行说明整理

#### 推荐分工

- 王胜晟：集成测试、CI/CD、Bug 日志、运行说明
- 王自宽：核心业务单元测试
- 蔡利扬：前端联调收尾、演示路径打磨

#### 说明

虽然这一阶段在最后集中收口，但测试不应完全拖到最后一天。  
尤其是订单状态流转、认证校验、评价逻辑，应该在实现时同步补核心单元测试。

---

## 4. 简化开发顺序表

### 顺序 1：最先做

- 工程骨架
- 数据库初始化
- 用户认证

### 顺序 2：主链入口

- 任务大厅
- 任务详情
- 发布需求

### 顺序 3：主链核心

- 申请接单
- 确认接单
- 创建订单
- 订单详情

### 顺序 4：主链闭环

- 订单状态流转
- 完成确认

### 顺序 5：支撑模块

- 通知
- 文件上传
- 订单内聊天
- 举报与公告后台

### 顺序 6：收尾与交付

- 单元测试
- 集成测试
- CI/CD
- Bug 修复
- 演示准备

## 5. 可并行开发模块汇总

| 阶段 | 可并行开发模块 | 说明 |
|------|----------------|------|
| 第一阶段 | 后端骨架 / 前端骨架 / 数据库初始化 | 三者耦合较弱，可以同步推进 |
| 第二阶段 | 用户认证后端 / 登录注册前端 / 测试账号准备 | 可边写接口边做页面 |
| 第三阶段 | 需求模块后端 / 任务大厅与发布前端 / 文件上传基础 | 发布需求和图片上传可并行 |
| 第四阶段 | 接单成单后端 / 订单页面前端 / 通知骨架 | 成单后很快要接通知 |
| 第五阶段 | 状态流转后端 / 状态展示前端 / 通知联动测试 | 主链闭环阶段适合小范围并行 |
| 第六阶段 | 评价后端 / 评价前端 / 评价通知与测试 | 评价是订单完成后的并行补充 |
| 第七阶段 | 通知 / 上传 / 聊天 / 举报 / 公告 | 在主链稳定后可多线推进 |
| 第八阶段 | 单测补齐 / 集成测试 / CI / Bug 修复 / 演示说明 | 收尾阶段适合分工并行 |

---

## 6. 不建议并行乱做的部分

以下内容不适合多人同时深改：

- `OrderService` 状态流转规则
- 数据库核心表结构频繁变更
- API 字段命名反复调整
- 权限规则和认证边界

原因是这些内容一旦变化，会连锁影响：

- 前端联调
- 通知和聊天逻辑
- 测试用例
- 数据库脚本

因此这些部分应有明确主负责人，并在修改前同步团队。

---

## 7. 结论

对我们当前的 `CampusHub` 项目来说，最合理的编码顺序不是“谁有空谁先做什么”，而是严格围绕依赖关系推进：

- 先做骨架和身份
- 再做需求发布与浏览
- 再做接单、订单和状态流转
- 然后补评价、通知、聊天、举报和公告
- 最后收口测试、CI 和演示

如果按这个顺序推进，3 人团队既能保持并行效率，又能避免主链尚未稳定时就过早陷入扩展功能开发。
