# P4 任务 1：Sprint 合并任务看板

## 1. 任务目标

本交付物用于把 `P0-P3` 已确定的需求、架构和详细设计，整理为可直接执行的编码开发任务板。  
任务拆解遵循以下原则：

- 只把 `P0` 核心功能和 `P1` 优先级功能纳入本阶段必做范围。
- `P2` 中已经明确不适合首版硬做的扩展能力，只做设计预留或放入可选任务。
- 单个任务尽量控制在 `2-4` 小时内，便于 3 人团队并行推进和每日同步。
- 任务完成标准以“可运行、可联调、可验证”为准，而不是只写出代码骨架。

---

## 2. 本阶段范围决策

### 2.1 本阶段必须完成

- 用户注册、登录、邮箱验证码、基础资料维护
- 游客/未认证用户浏览公开需求
- 已认证用户发布需求、查看自己发布的需求
- 任务大厅的分类/校区筛选、关键词搜索和基础排序
- 服务方申请接单，需求方确认接单
- 订单创建、订单详情、订单状态流转、订单历史
- 订单完成确认与双向评价基础版
- 系统通知基础版
- 举报提交与管理员处理基础版
- 基础后台中的用户禁用/解禁能力
- 单元测试、集成测试、CI 基础流程

### 2.2 本阶段做基础版即可

- 订单内聊天：先支持文字消息和图片消息的基础收发，不追求完整 IM 体验
- 公告：先完成基础发布与前台查看
- 文件上传：先满足头像、任务配图、聊天图片、举报证据四类基础场景
- 忘记密码与邮箱验证码重置：如主链稳定则补充基础流程，不作为首个联调阻塞项

### 2.3 本阶段暂缓或降级

- 智能匹配
- 复杂统计分析
- 复杂申诉/仲裁细分流程
- 需求收藏
- 通知删除与消息删除
- 黑名单完整联动
- 推荐算法、多学校部署、在线支付

## 5. Sprint 节奏安排

### Sprint 1：骨架与主链入口

- 初始化前后端工程
- 导入数据库
- 完成注册、登录、任务大厅、任务详情基础版

**阶段目标：** 系统能启动，游客可浏览公开需求，用户可注册登录。

### Sprint 2：发布需求与接单成单

- 发布需求
- 申请接单
- 确认接单
- 创建订单
- 订单详情联调

**阶段目标：** 完成“发布需求 -> 申请接单 -> 生成订单”主链路。

### Sprint 3：订单闭环与支撑能力

- 订单状态流转
- 完成确认
- 评价
- 通知
- 聊天
- 举报/公告/文件上传基础版

**阶段目标：** 完成“订单执行 -> 完成 -> 评价/通知/举报”闭环。

### Sprint 4：测试、CI 与演示收尾

- 单元测试补齐
- 集成测试
- CI 配置
- Bug 修复
- 演示说明和运行说明整理

**阶段目标：** 系统可稳定演示，具备基础自动化检查能力。

## 6. AI 辅助 Sprint 规划记录

### 6.1 AI 可辅助的部分

- 根据 `P1-P3` 文档初步拆分任务
- 给出首轮工时估计
- 帮助识别哪些模块依赖更强、联调风险更高
- 生成任务板初稿和状态字段模板

### 6.2 需要人工确认的部分

- 哪些功能必须进入本阶段交付
- 哪些功能只做基础版，不追求完整体验
- 哪些任务应该由谁主导，避免多人同时改同一核心模块
- 工时估计是否符合我们 3 人团队的真实节奏

### 6.3 本次人工调整结论

- 将 `OrderService` 相关任务集中给 1 人负责，保证订单状态一致性。
- 将通知、举报、上传、CI 等支撑任务集中给 1 人，避免主链被支撑功能拖慢。
- 将前端页面与联调整体交给 1 人，减少“接口写好了但页面接不上”的风险。
- 把 `P2` 扩展功能降为可选项，避免影响 `P0/P1` 主流程交付。

## 7. 风险与应对

| 风险 | 影响 | 应对方式 |
|------|------|----------|
| 订单状态流转多人同时修改 | 容易引入非法状态和联调错误 | 由王自宽统一负责订单状态规则，其他人通过接口使用 |
| 前后端接口字段不一致 | 联调失败、返工 | 每次接口调整同步更新 `P3 API` 和联调清单 |
| 聊天/通知占用过多时间 | 拖慢核心主链 | 先保证基础版，仅做必要场景，不追求完整 IM 能力 |
| 测试和 CI 被拖到最后 | 难以及时发现回归问题 | 从 Sprint 2 开始同步补单测，Sprint 4 集中收口 |
| P2 扩展任务过早开始 | 影响 P0/P1 交付 | 所有 P2 任务必须在主链稳定后再进入开发 |

---

## 8. 结论

本阶段的编码开发应坚持“先主链、后扩展；先可跑、后优化；先测试核心规则、再补界面细节”的策略。  
对于我们 3 人团队来说，最关键的不是一开始功能做得多，而是先把 `注册登录 -> 浏览需求 -> 发布需求 -> 接单成单 -> 完成评价` 这条主业务链稳定跑通，再逐步补齐通知、聊天、举报和后台能力。
