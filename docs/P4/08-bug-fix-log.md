## 3. 详细修复记录

### Bug 1：邮箱验证接口返回结构与前端不一致

**问题现象**

前端完成邮箱验证后期望接口返回 `{ verified: true }`，但后端原接口返回空结果，导致前端无法根据响应判断邮箱是否验证成功。

**根因分析**

接口契约没有与前端页面状态绑定。后端只把验证结果写入数据库，没有提供前端需要的结构化状态字段。

**修复方案**

新增邮箱验证响应对象，将验证接口改为返回 `verified` 字段，使前端能够直接根据接口结果更新页面状态。

**验证结果**

邮箱验证流程可返回明确的验证状态，前端能够根据 `verified` 字段完成后续注册或提示逻辑。

### Bug 2：举报证据上传后未与举报记录建立持久关联

**问题现象**

前端可以上传举报证据图片并在提交举报时携带证据 ID，但后端只接收这些 ID，没有将证据与举报记录建立数据库关联。

**根因分析**

举报表只保存举报主体信息，缺少举报证据关联表；服务层没有把 `evidenceImageIds` 持久化为可追溯关系。

**修复方案**

新增 `report_evidence` 关联表和对应实体、Mapper。举报提交成功后，将证据文件与举报记录建立映射关系。

**验证结果**

举报提交后证据能够随举报记录保存，管理员后续可通过举报记录追踪对应证据。

### Bug 3：订单详情中的 `completionNote` 错误返回为取消原因

**问题现象**

订单详情页展示完成说明时，后端把 `cancelReason` 填入 `completionNote`，导致完成说明显示为取消原因。

**根因分析**

订单详情组装逻辑复用了错误字段，没有从订单状态日志中提取“提交完成”对应备注。

**修复方案**

调整订单详情转换逻辑，不再从 `cancelReason` 获取完成说明，改为从状态日志中提取最近一次提交完成备注。

**验证结果**

订单详情页的完成说明与取消原因分离，完成提交说明能够正确展示。

### Bug 4：任务配图、聊天图片、举报证据使用时缺少用途校验

**问题现象**

业务侧只根据文件 ID 查询文件记录，没有校验文件用途，导致任务配图、聊天图片、举报证据之间可能互相复用。

**根因分析**

文件服务只做了归属校验，缺少业务用途维度的校验，无法保证上传文件被用于正确场景。

**修复方案**

在文件服务中补充“归属 + 用途”双重校验。任务配图限定 `TASK_IMAGE`，聊天图片限定 `CHAT_IMAGE`，举报证据限定 `REPORT_EVIDENCE`。

**验证结果**

不同业务类型的上传文件不能跨用途复用，文件使用路径更加符合业务语义。

### Bug 5：注册验证码发送逻辑错误要求邮箱必须已存在

**问题现象**

新用户注册前发送验证码时，后端要求邮箱必须已存在，导致未注册用户无法获取注册验证码。

**根因分析**

验证码发送逻辑没有区分 `REGISTER` 和 `RESET_PASSWORD` 两种业务场景，把找回密码的邮箱存在性规则错误套用到注册场景。

**修复方案**

按验证码用途拆分校验规则：注册场景要求邮箱尚未注册；重置密码场景要求邮箱已经注册。

**验证结果**

未注册邮箱可以正常获取注册验证码，已注册邮箱会被注册发码流程拒绝。

### Bug 6：上传成功后的图片 URL 可能被安全策略拦截

**问题现象**

文件上传接口返回成功，但浏览器访问 `/uploads/**` 图片资源时可能出现 401 或 403，页面无法显示上传图片。

**根因分析**

后端虽然配置了上传目录静态映射，但 Spring Security 没有放行 `/uploads/**` 静态资源路径。

**修复方案**

在安全配置中将 `/uploads/**` 加入白名单，允许浏览器直接访问上传后的静态资源。

**验证结果**

头像、任务配图、聊天图片和举报证据可以通过返回 URL 正常加载。

### Bug 7：头像更新未经过文件归属与用途校验

**问题现象**

更新个人资料时，后端直接信任前端传入的头像 URL，未验证该文件是否属于当前用户、是否为头像用途。

**根因分析**

头像更新逻辑绕过了统一文件服务校验，存在误用他人文件或错误用途文件的风险。

**修复方案**

根据头像 URL 反查 `file_record`，校验文件归属当前用户且用途为 `AVATAR` 后再写入资料。

**验证结果**

只有当前用户上传的头像文件可以被设置为个人头像。

### Bug 8：完成凭证可复用任意自有上传文件

**问题现象**

服务方提交订单完成凭证时，只要文件属于当前用户即可被使用，未限制必须是订单完成凭证用途。

**根因分析**

订单完成流程缺少 `ORDER_PROOF` 业务用途校验，文件用途边界不清晰。

**修复方案**

新增 `ORDER_PROOF` 文件用途，订单完成时要求凭证文件属于当前用户且用途为 `ORDER_PROOF`。

**验证结果**

订单完成凭证只能使用对应用途的上传文件。

### Bug 9：注册接口未校验验证码

**问题现象**

注册接口只校验邮箱、密码和重复注册，没有校验注册验证码，用户可能绕过邮箱验证直接注册。

**根因分析**

验证码发送和注册提交是两个独立流程，注册服务没有查询并校验最近一条未使用的 `REGISTER` 验证码。

**修复方案**

在注册请求中补充验证码字段。注册时校验验证码存在、用途匹配、未过期且未使用，注册成功后标记验证码已使用。

**验证结果**

未携带或携带错误验证码的注册请求会被拒绝，邮箱验证成为注册必要步骤。

### Bug 10：任务大厅非法分类参数会返回 500

**问题现象**

任务大厅接口接收非法分类参数时，后端抛出 `IllegalArgumentException`，最终返回服务器内部错误。

**根因分析**

分类解析直接调用 `TaskCategory.valueOf(category)`，没有把非法枚举值转换为业务参数错误。

**修复方案**

封装安全分类解析逻辑，非法分类值主动抛出 `BusinessException(ErrorCode.BAD_REQUEST)`。

**验证结果**

非法分类参数返回明确的 400 参数错误，不再表现为 500。

### Bug 11：更新资料接口缺少 `@Valid`

**问题现象**

`UpdateProfileRequest` 中配置了字段长度约束，但接口参数未加 `@Valid`，参数约束没有生效。

**根因分析**

Controller 层没有触发 Bean Validation，DTO 上的注解只停留在定义层。

**修复方案**

在更新资料接口请求参数上补充 `@Valid`。

**验证结果**

超长昵称、简介等非法资料输入可以被后端参数校验拦截。

### Bug 12：数据库连接编码参数错误导致登录时报 500

**问题现象**

前端切换真实后端后，登录接口返回 500，后端控制台提示 `Unsupported character encoding 'utf8mb4'`。

**根因分析**

JDBC URL 的 `characterEncoding` 使用了驱动不支持的 `utf8mb4` 写法。

**修复方案**

将 JDBC URL 中的 `characterEncoding=utf8mb4` 改为 `characterEncoding=UTF-8`。

**验证结果**

后端能够正常连接 MySQL，登录接口不再因编码参数错误失败。

注册页新增发送验证码按钮和验证码输入框，注册 API 补充 `code` 字段，mock 同步真实后端规则。

### Bug 16：真实后端验证码没有实际发送邮件

**问题现象**

后端生成验证码并写入数据库，但用户点击发送验证码后收不到邮件，前端真实后端模式仍提示 mock 固定验证码。

**根因分析**

验证码服务只打印日志，没有调用邮件发送服务；前端提示文案也没有区分 mock 和真实后端。

**修复方案**

新增 `EmailService`，支持 `smtp` 和 `log` 两种投递模式。验证码入库后调用邮件服务发送，失败时返回明确业务错误并回滚验证码记录。前端按模式区分提示文案。

**验证结果**

配置 SMTP 后可真实发送验证码；本地无 SMTP 时可切换日志模式完成开发联调。

补充资源地址解析工具和 Vite `/uploads` 代理，将上传资源正确指向后端服务。

**验证结果**

上传后的图片可以在任务发布、任务详情、聊天和举报证据场景正常预览。

### Bug 19：用户资料接口返回的信用数据是写死值

用户资料页显示的信用分、完成订单数和好评率为固定值，不能反映真实订单和评价数据。

### Bug 20：确认接单流程缺少并发保护

**问题现象**

多个申请同时被处理时，可能出现重复成单或多个申请被错误通过。

**根因分析**

确认申请流程只在内存对象上判断状态，没有使用条件更新保证任务和申请状态转换的原子性。

**修复方案**

使用带当前状态条件的更新语句处理任务和申请状态，并将确认接单逻辑放入事务。

**验证结果**

同一任务只能成功确认一个申请，重复或并发确认会被业务错误拦截。

### Bug 21：后台订单恢复接口请求语义与实际结果不一致

**问题现象**

管理员恢复争议订单时，请求状态和实际恢复状态可能不一致，前端难以判断最终结果。

根据管理员操作日志读取争议前状态，要求恢复请求中的目标状态与原状态一致后才允许恢复。

**验证结果**

订单恢复接口语义明确，恢复结果与请求目标保持一致。

### Bug 25：任务编辑、删除、收藏与申请拒绝接口约束不完整

任务编辑、删除、收藏、拒绝申请等接口在部分状态下行为不稳定，可能允许不应发生的操作或返回不完整状态。

**验证结果**

任务相关操作的权限、状态和返回结果与业务规则一致。

### Bug 53：服务方取消成功后“我的订单”仍显示该订单

**问题现象**

服务方取消服务并由发布方同意后，该订单仍出现在服务方“我的订单”中，并标记为“我接单”。

**根因分析**

订单虽然已经退回待接单，但查询和前端关系判断仍根据历史服务方字段把该订单视为服务方相关订单。

**修复方案**

后端订单列表在服务方视角排除 `PENDING_CONFIRM` 和 `CANCELLED` 状态订单；前端“我的订单”也对待接单状态做兜底过滤，避免历史服务方继续看到该订单。

**验证结果**

服务方取消并经发布方同意后，该订单不再出现在服务方“我的订单”列表；发布方仍能看到并继续管理该需求。

**验证结果**

从“我的订单”进入退回待接单的详情页后，右侧可以看到需求管理和接单申请模块，操作入口与任务大厅详情页保持一致。

### Bug 55：已取消的接单申请仍显示确认和拒绝按钮

### Bug 56：需求编辑和删除按钮位置与禁用交互不一致

**问题现象**

**根因分析**

两个入口使用了不同的按钮布局，且禁用态使用原生 `disabled`，导致按钮灰显后点击事件被浏览器吞掉，无法给用户解释原因。

**修复方案**

**验证结果**

两个入口的需求管理布局一致；已接单或已有接单申请时按钮灰显，点击会提示“已有接单或接单申请，不能编辑/删除该需求”。

### Bug 60：失物招领时间字段语义不清且被错误限制为未来时间

**问题现象**

**根因分析**

动态字段只按字段名 `foundTime` 简单转为“时间”，没有体现业务含义；未来时间限制按 `*Time` 字段统一套用，没有区分“事件发生时间”和“活动时间”。

**修复方案**

**验证结果**

失物招领可以选择过去的丢失或捡到时间；组队活动时间仍只能选择未来时间。

### Bug 61：发布需求页匿名发布复选框选中后被撑成横条

**问题现象**

发布需求页勾选“匿名发布”后，复选框显示为横向长条，对勾位置看起来歪斜。

**根因分析**

全局普通输入框样式给 `.field input` 设置了 padding，`input[type='checkbox']` 虽然设置了宽高，但仍继承了输入框 padding，导致实际宽度被撑大。

**修复方案**

在全局 checkbox 样式中清除 padding，设置 `box-sizing: border-box`，并移除普通输入框背景图影响。

**验证结果**

匿名发布复选框保持固定方形尺寸，选中后的对勾居中显示。

### Bug 62：发布需求页时间限制只覆盖截止时间，动态时间字段未按语义处理

**问题现象**

发布需求页主“截止时间”已限制未来时间，但分类动态字段中的时间仍可能缺少限制或被错误限制。浏览器日期选择器中，过去日期可被选中或字段语义与限制不一致。

**根因分析**

主截止时间使用了 `min` 和提交校验，而动态字段根据 key 生成输入框时没有统一处理 `datetime-local` 的最小值；后续按 `*Time` 一刀切限制又误伤了失物招领的事件时间。

**修复方案**

将动态时间字段拆分为“日期时间字段”和“必须未来的日期时间字段”。仅 `activityTime` 等未来活动时间设置 `minDeadline` 并在输入、变更、失焦和提交前校验；失物招领的 `foundTime` 不再限制未来。

**验证结果**

主截止时间和组队活动时间不能选择过去时间；失物招领的丢失/捡到时间允许选择过去时间，符合业务语义。
